# Applying and evaluating EDSO

## A first deployment

Start with one feeder-load forecast. The operator publishes identifiers for a versioned data product and semantic profile. The local connector exports the decision reference, the orchestrator exports update and checkpoint references, and the evaluator exports one scored run. These records can be transformed from existing CSV or JSON logs. Each organisation remains authoritative for the records it produces. Where metadata itself is sensitive, use scoped identifiers and authorised views. Public examples should contain fictional entities.

| Source field or record | RDF representation | Identity or mapping decision |
|---|---|---|
| Catalogue product ID, revision, observation interval and mapping version | dcat:Dataset, dcat:version, dcat:temporalResolution, dct:conformsTo | Mint one IRI per snapshot. Distinguish metering interval from forecast horizon. Publish the version of the specific mapping profile. |
| CIM/CGMES feeder identifier or SAREF flexibility offer | Domain resource in the source graph, linked via dct:subject when the dataset is about it | Preserve the model edition, source identifier and unit. Agreement on a feeder name alone is insufficient across networks. The flexibility fragment shows the ETSI class names. |
| Connector request ID, dataset, action, service principal, disposition, decision time and policy ID | edso:UseDecision with explicit requester, attribution and policy version | Keep a refusal as a decision record. Only executed jobs enter the training lineage. A partner may publish an opaque identifier for an internal record. |
| Local job ID, update digest, aggregation round and checkpoint digest | LocalContribution, an update generated by it, FederatedTrainingRound and a generated checkpoint | Mint immutable references for inputs and outputs. Several local activities can share one round. Model hash and release label serve different purposes. |
| Privacy accountant report | PrivacyAccount with scope, population, unit, adjacency, accountant, epsilon, delta and source reference | Obtain the bound from the accountant. A cumulative bound requires an explicit activity sequence and a compatible accounting scope. |
| Model registry release and model card | FoundationModelRelease with version, licence, derivation and dct:references | Use a new release IRI when weights or adapters change. Track preprocessing and calibration artifacts in the immutable release manifest. |
| Scoring harness and TEF result export | EvaluationRun and EvaluationScore | Freeze the holdout manifest, horizon, protocol, baseline, scenario and unit. Retain the site identity and responsible evaluator separately. |
| Technical review package | EvidenceBundle with deployment context, attributed reviewer and members | Link to reports at appropriate access levels. A later review can create a new bundle and refer to the earlier one using PROV. |

## Measuring the added value

1. **Select three questions before partner mapping.** Trace a TEF result back to the authorised local inputs, find downstream results affected by a policy revision, and determine which scores can be directly compared. Have each partner provide expected answers, including cases where the answer is unknown.
2. **Use a serious baseline.** Give one mapping team the same source records, OMEGA-X, MLDCAT-AP, PROV-O, ODRL and their published guidance. Give a second team those resources plus EDSO and its shapes. Allow both teams to compose terms. Record the extra local terms, joins, assumptions and mapping time for each team. If both recover the same answers at similar cost, report that result.
3. **Evaluate on an unseen export.** Develop the mapping on a gym trace. Freeze EDSO and the questions. Ask a TEF to map its own independently produced report without seeing the gym transformation. Use at least one different scenario and one missing field. Score each query against the agreed answers using precision, recall and correctly reported unknowns. Separately report which records the shapes reject and why.
4. **Check portability across energy tasks.** Repeat with a congestion or anomaly model, where the event, its forecast and time of detection have distinct identities. Then use a flexibility or V2G model, where forecast accuracy, dispatch feasibility, offered power and delivered energy are different quantities. Add a term only for a question the current profile cannot answer.
5. **Publish reproducible evidence.** Release approved sanitised fixtures or synthetic equivalents, mappings, query results, time spent and unresolved mappings. Track ontology version, source profile editions and scoring harness revision. A useful negative result is a valid TEF report with a different holdout or horizon that the matched-score query correctly excludes.

## Project integration and community release

| Workstream | Proposed contribution |
|---|---|
| Common data models and semantic profiles | Offer the profile and mapping tests to the project task lead. Ask operators to identify the actual CIM/CGMES edition and one representative input field per use case. |
| Federated execution, synthetic data and model registry | Add a metadata export at job completion and release creation. Link synthetic utility and privacy evaluations separately from fidelity. |
| Independent validation and governance | Agree a small TEF evidence exchange with the evaluator before the first test. Make controlled-access review bundles resolvable to authorised reviewers. |
| Community adoption | Ask a second operator or TEF to run the same questions on its own exports. Present the resulting mappings and failures to energy data-space and ML metadata maintainers. |

The first tagged release should identify contributors, the maintained namespace and redirect owner, version and deprecation rules, the profile editions tested, and the tested scope of each mapping. An archival DOI can then cite the exact release. Those steps and any formal adoption are future milestones.

## Open design questions for partners

- Which operator identifiers may leave the site, and what coarser identifiers preserve the answers a TEF needs?
- Does the connector supply a decision event even when consent or a contract changes after training? What effective dates and allowed purposes can be shared? A policy-impact result identifies records for human review.
- Which releases require a dependency graph over multiple checkpoints or reused third-party backbones? Can the hub export those edges with a stable identity?
- Which TEF outputs include hardware-in-the-loop configuration, time-window manifests, uncertainty and repeated runs? Which deviations are intentionally part of a stress test?
- Which institutions are responsible for assigning TRL or making an applicable regulatory assessment, and which individual evidence items are public?
